# Обязательные поправки к ТЗ Argon для Gemini 3.8

Дата: 31 октября 2026 года. Это **дополнение к присланному ТЗ, не новый roadmap и не разрешение на внешние операции**. При конфликте применять ограничения этого документа. Базовый план остаётся `.hermes/plans/2026-10-30_150846-product-to-telegram-and-revenue.md`; результаты исходного review — `docs/audit/2026-10-31-antigravity-k2-review.md`.

Проверенный исходный HEAD: `5f39a90`. На момент проверки продуктовые файлы ещё не изменены относительно него. Живые процессы и реальные БД в этом review не проверялись повторно. Порядок: сначала узкое P0-исправление; затем контракт хранения; затем подключение существующего UI и тесты; после этого отдельный согласованный внешний показ. Один интегратор, без редизайна, смены стека и дополнительных функций.

## 1. Не оставлять гостевую авторизацию в пользовательском пилоте

Удалить обходы подписи и авторизацию по присланному user_id. Исправление требуется на реальных handlers, не только в HMAC-helper.

**Поправка к блоку 1:** условие `not is_production` не означает «только локальный preview». В `bot/app_settings.py:20,28,35–36` режим по умолчанию `pilot`, anonymous preview включён, а production — лишь имена `production`/`prod`. Предлагаемое ТЗ поэтому допускает общую гостевую запись 1000 в публичном пилоте без signing key.

В этом срезе не нужна гостевая сессия для защищённых API: и production, и `k2-pilot` требуют валидную подпись при создании сессии и валидную Bearer-сессию для персональных данных. Нет configured signing key — отказ, не guest. Нет Telegram initData при обычном открытии браузером — понятное «Открой приложение в Telegram» либо отдельно обозначенный read-only preview без обращения к персональным API/БД. Preview не превращается в запись пользователя 1000.

Неверный/пустой/просроченный Bearer не откатывается к guest. Если предоставлены query и header IDs, проверять каждый относительно verified session. Без сессии они не удостоверяют личность. Все tests используют синтетически подписанные данные и временную БД. Запрещён именно bypass по содержимому запроса; `unittest.mock` в тестах или подписанное имя, содержащее слово mock, не являются нарушением.

## 2. Сначала контракт и сохранение в БД, затем fetch в UI

**Пропуск в ТЗ:** `bot/app_models.py:24–28` и `bot/app_db.py:187–220` сейчас не сохраняют menu, checked_ingredients, checked_steps, shopping_portions, shopping_stale. `PUT /api/user` принимает Dict и может вернуть 200, пока эти поля молча теряются. Профиль также не сохраняет все поля `UserSettingsDraft`.

Обязательная область изменений: `bot/app_models.py`, `bot/app_db.py`, `bot/server.py`, тесты `tests/backend/test_app_models.py`, `test_app_db.py`, `test_user_api.py`; после этого `src/api/ketoClient.ts` и `src/ui/food-first/FoodFirstApp.tsx`. Не ограничивать работу добавлением client-side запросов.

До UI зафиксировать типизированный и версионированный payload сохранения. В него входят каноническое меню, выбранная **дата** из menu.days, необходимые настройки/ограничения, отметки ингредиентов и шагов, выбор порций/выхода и stale-состояние покупок. Имена wire-полей, nullable-правила и mapping перечислить в текущем release-срезе до реализации. Условный `dayIndex` остаётся presentation-only; основной `GeneratedMenu` имеет date/slots/числовой created (`src/domain/types.ts:29–41`). Сохранение произвольного маршрута не добавлять как новую обязательную функцию: при открытии можно показывать Сегодня с восстановленными данными.

UI shopping item (`src/ui/food-first/contract.ts:65–72`) содержит `amountLabel`, `alreadyHave`, `checkedInStore`; backend ShoppingItem (`bot/app_models.py:30–40`) требует числовые amount/unit и один checked. Нужен явный сохраняющий данные mapping/контракт. Не превращать «по вкусу»/неизвестное количество в 0 ради schema validation и не терять один из двух флагов.

Критерий до подключения UI: полная сериализация тестового snapshot → save → read → deep equality по всем согласованным полям. Неизвестные поля должны отклоняться либо обрабатываться явно, а не приниматься с ложным 200 и потерей данных. Код изменения схемы и совместимость проверять только на синтетической БД; рабочую БД не мигрировать.

## 3. Не допустить перезаписи сохранённого состояния при старте

Явные фазы: authenticating → loading → ready/error. До successful загрузки собственных profile/state/shopping **запрещён autosave defaults**. Server state имеет приоритет над пустыми начальными React states.

Кеш привязан к verified user ID и версии схемы; нельзя загружать общий старый `kb_proto_*` как персональное состояние другого пользователя или отправлять его под новой сессией. Token не записывать в обычный localStorage-кеш. Нет профиля — не выставлять автоматически confirmed18Plus/isSaved и не выдавать sample за персональное меню.

Для первого среза offline — read-only с честным статусом, без новой очереди offline writes. Ошибки 401/сети не маскировать гостевым входом или сообщением «сохранено». Последовательные изменения не должны откатываться поздним ответом устаревшего PUT. Минимальный regression: уже сохранённый на сервере snapshot при задержанном initial GET не перезаписывается default snapshot до загрузки.

## 4. Не утверждать каталог и нутриенты технической синхронизацией

**Заменить автоматическое заполнение k1–k15.** Эти IDs — предложение набора, не доказательство допуска владельцем. Пока конкретные рецепты не допущены, production allowlist остаётся пустым; API и UI должны честно сообщать об отсутствии допущенного набора. В тестах применяется явный синтетический manifest, который не является публикацией реальных блюд. Не подгонять tests под магическое число 15 вместо проверки состава допуска.

Один допущенный пул используется в catalog API, генерации, заменах, отображении и покупках через существующий controller/release boundary. Прямой импорт всего RECIPES в recipesAdapter недопустим для live режима. Backend catalog для тестов должен получать fixture/provider, а не читать настоящий bot_data.json.

**Не удалять `[УТОЧНИТЬ]` по факту наличия чисел.** В каноническом Recipe поля `kcal`, `p`, `f`, `nc`, а не `b`, `zh`, `u` (`src/domain/types.ts:13–16`). `nc` не переименовывать молча в общие углеводы. Наличие этих значений в исходнике не подтверждает источник, единицы и «на 1 порцию». В существующем `src/adapters/foodView.ts:19–27` намеренно сохраняются sourceYield, исходные строки и `[УТОЧНИТЬ]`.

Для быстрого первого выпуска выбрать уже допустимый вариант ТЗ: показать **базовый выход рецепта и исходные количества**, не обещая неподтверждённый пересчёт на 1/2 порции. Не применять `serv || 1` к неизвестному/повреждённому выходу. Масштабирование и числовые КБЖУ включаются только после утверждённой семантики/источников и тестов; не менять формулы/ценники ради зелёных проверок.

## 5. Не подменять поддержку номером ticket

`POST /api/support` сейчас лишь сохраняет запись (`bot/server.py:290–308`), не доставляет её Ольге. HTTP 200 и ticket_id не доказывают получение вопроса.

Для первого выпуска сохранить **один существующий маршрут вопроса Ольге через бот** и проверить его отдельным согласованным nonsensitive сообщением. Не строить вторую очередь обращений и новую форму только ради наличия POST в E2E. Если форма всё же входит в отдельно согласованный scope, различать «сохранено в сервисе», «доставлено Ольге» и «доставка неизвестна/ошибка»; не обещать ответа без рабочей обработки. Авторизация и исходящие реальные сообщения — разные разрешения.

## 6. E2E должен быть реальным по стеку, но изолированным по данным

**Не запускать новые пишущие E2E как есть на 8000.** В `playwright.full.config.ts:18,24–27` указан этот порт и `reuseExistingServer:true`. Исполнение присланного ТЗ с PUT/DELETE/созданием обращений может использовать уже работающий сервер с его БД.

До пишущих тестов подготовить test-only startup на отдельном loopback-порту, например `127.0.0.1:18080`, с `reuseExistingServer:false`. Если порт занят — остановить тест, не чужой процесс. BaseURL, health URL и фактический порт test-server обязаны совпадать.

Только новая БД в Hermes scratch, непустой тестовый signing key, синтетический catalog provider, `KETO_LOAD_DOTENV=0`, отключённые оплаты и запрет внешних сервисов. Настоящие .env, bot_data.json, .tunnel_cache.json, runtime logs и данные участников не читать. Не запускать Telegram polling. Не выполнять production migrations.

Тестовые HTTP API действительно обслуживаются FastAPI/SQLite, а не `route.fulfill` ответами. Подписанный fixture initData передаётся браузеру через test fixture; signing key не встраивается в product frontend. BrowserContext новый, не профиль владельца. Нельзя очищать localStorage действующего браузера владельца.

Persistence acceptance: пользователь A меняет допущенный рецепт/выбранную дату/покупку; дождаться подтверждённого server save; закрыть context; новый context без localStorage/sessionStorage получает свежую подписанную тестовую Telegram identity A; восстановить полный snapshot с сервера. Пользователь B не видит/не перезаписывает A. Проверить отказ сети и отсутствие ложного «сохранено». Открытие секции поддержки проверяется отдельно от реальной доставки.

`grep` и факт наличия fetch — вспомогательные source checks, не приёмка. Не запускать голый `npx playwright test` с неизвестным default config или полный gate, пока изоляция всех его дочерних команд не обеспечена.

## 7. Честный статус и окончание работы

Плашка preview убирается не потому, что «некрасиво называться макетом», а только когда для данной сессии реально завершена интеграция. До этого показывать «Демонстрационный режим»; после — фактический статус загрузки/сохранения/ошибки. Визуальное направление не переделывать.

Локальная интеграция PASS не означает K1/K2 принят в Telegram. Внешний HTTPS, привязка тестового входа и настоящий nonsensitive support test выполняются лишь в отдельно согласованном operational scope; не читать/редактировать .env и не перезапускать туннель ради локального теста. Состояния S-PUBLISH/S-PILOT-DEPLOY в рассмотренном owner-decisions остаются proposed; данный файл их не утверждает.

Конечный пользовательский результат прежний: владелец открывает идентифицированную сборку через Telegram, проходит меню → рецепт → покупки и повторно входит с восстановленными данными. В отчёте разделить закрытие P0, локальный server round-trip, browser integration, внешний маршрут и приёмку владельца. Нет конкретного доступного входа — не «K2 готов на 100%».

Границы: сохранять чужие изменения, не выполнять commit/push/deploy, не трогать настоящие секреты/БД, цены и математические формулы, не запускать платежи/рассылки/внешние AI. Кабинет НутриОК на 8090 — отдельный проект и не цель этого пакета.
