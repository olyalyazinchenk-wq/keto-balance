## 3. Независимое восстановление процессов и туннеля (Task 2)

1. **Раздельная проверка компонентов**:
   - Функции `start()` и `supervisor()` проверяют сервер и туннель независимо друг от друга.
   - Если живой сервер отвечает на порту 18081, он **сохраняется без перезапуска**.
   - При сбое туннеля перезапускается **исключительно туннель**, бэкенд не затрагивается.
2. **Изолированное управление процессами и дочерним `ssh.exe`**:
   - **Исключено завершение процессов по адресу/порту**: в `scripts/home_pilot.py` (строка 267) полностью удалено завершение процессов-сирот, найденных только по сетевому адресу/порту (`query_orphan_ssh_pids`).
   - **Строгая верификация перед остановкой**: функция `safe_terminate_process` разрешает остановку только своего процесса при одновременном совпадении трёх параметров:
     1. Зафиксированный PID.
     2. Подтверждённое время создания процесса (`create_time`).
     3. Полный абсолютный путь к исполняемому файлу (`executable`, `os.path.isabs`).
   - При отсутствии подтверждения или несовпадении любого из параметров чужой процесс **категорически не трогается** (`[WARN] Process not killed`).
   - В `scripts/run_ssh_tunnel.py` функция `record_ssh_state` сохраняет в `.tunnel_ssh_state.json` точный PID, `create_time` и полный абсолютный путь к `ssh.exe`.
   - В `cleanup_tunnel_ssh(port)` завершение дочернего SSH выполняется строго на основании подтверждённого `.tunnel_ssh_state.json`. При отсутствии файла состояния или отсутствии сохранённого `executable` чужие процессы не затрагиваются (подстановка пути из активного процесса устранена).
   - Посторонние сессии SSH и процессы смежного проекта НутриОК в системе **полностью защищены**.
3. **Экспоненциальный бэкофф супервизора**:
   - Расписание задержек: `5, 10, 20, 40, 60 секунд`.
   - После 5 последовательных неудач супервизор останавливается (`Halting supervisor`).
   - Счётчик сбоев сбрасывается **только после подтверждённой готовности** (`check_ready() == True`).

## 4. Доверенная проверка готовности и Pinned Build (Task 3)

1. **Фиксация Build Receipt**:
   - `receipt_path` явно сохраняется в `.home_pilot_state.json` и передаётся серверу аргументом `--receipt <path>`.
   - При восстановлении проверяется наличие самой квитанции и директории `dist_dir` с файлом `index.html`. Откат на корень `dist` без квитанции строго запрещён.
2. **Режимы готовности**:
   - `LOCAL_READY`: Проверяет доступность локального порта 18081 и `/api/health` бэкенда, сверяя хэши с квитанцией.
   - `PUBLIC_READY`: Выполняет все проверки `LOCAL_READY` плюс опрашивает публичный HTTPS URL туннеля (`/api/health`, `/api/version`), гарантируя, что через туннель отдаётся именно зафиксированная сборка и полезная нагрузка совпадает с локальной.
3. **Защита от ложных срабатываний**:
   - HTML-ответы (например, 200 OK от страницы ошибки Cloudflare/localhost.run) отклоняются, требуется валидный JSON.
   - Конечные слэши в URL туннеля нормализуются (`.rstrip("/")`), исключая генерацию ошибочных путей `//api/health` (HTTP 404).
   - Ошибки HTTP (502, 404) не зацикливаются через повторные запросы в локальный прокси.
   - Все 8 негативных сценариев протестированы и блокируют готовность:
     1. Локальный порт не слушает.
     2. `/api/health` бэкенда недоступен.
     3. Несоответствие `buildId`.
     4. Несоответствие `backendFingerprint`.
     5. Несоответствие `catalogHash`.
     6. Отсутствие внешнего URL в `current_tunnel_url.txt`.
     7. Внешний URL отдаёт ошибку HTTP 502 / 504.
     8. Внешний туннель отдаёт не ту сборку или HTML вместо JSON.
4. **Сквозные коды возврата**:
   - `ops/start-keto-balance.ps1` и `ops/status-keto-balance.ps1` возвращают `exit $LASTEXITCODE` (0 при успехе, 1 при сбое).
