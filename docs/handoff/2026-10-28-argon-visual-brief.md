## 6. Визуальная концепция

### Основное направление A — «Спокойная кухня»

Продолжение исходного «Кето Баланс»: тёплый молочный фон, белые поверхности, шалфейный акцент, тёплый тёмный текст, крупная привлекательная еда. Спокойная уверенность и бытовая полезность вместо лаборатории и спортивной аналитики.

Предлагаемая исходная палитра, не медицинская цветовая шкала:

| Токен | Значение | Назначение |
|---|---|---|
| background | `#F7F2E9` | фон |
| surface | `#FFFFFF` | поверхности |
| ink | `#2B2620` | основной текст |
| primary | `#5F7161` | основное действие |
| muted | `#625C54` | вторичный читаемый текст |
| sage | `#EDF1E6` | мягкое выделение |

Расчёт контраста этих плоских пар: ink/background — 13.44:1; muted/surface — 6.61:1; белый/primary — 5.22:1; primary/sage — 4.56:1. Это не проверка всего экрана: заново проверь реальные размеры, состояния, наложения и изображения.

- Сначала композиция каждого экрана, потом украшения. Главная — помощь с ближайшим действием; меню — выбор; покупки — выполнение; рецепт — чтение во время готовки. Не штампуй одинаковую сетку карточек на всех экранах.
- Типографика: осознанно выбранный читаемый шрифт с полноценной кириллицей; базовый текст 16px, вторичный обычно не менее 14px, заголовки по иерархии. Не меняй кириллицу на случайный системный fallback. Локальные шрифты предпочтительнее внешних Google Fonts; не добавляй тяжёлые зависимости ради одного начертания.
- Одна главная кнопка на смысловой блок; ясные глаголы: «Выбрать меню», «Собрать покупки», «Начать готовить», «Записать приём пищи», «Написать Ольге».
- Аккуратные радиусы и отступы из общей шкалы; единая толщина иконок; эмодзи умеренно. Никаких неоновых градиентов, glassmorphism и «медицинского синего» по умолчанию.
- Фотографии — локальные, с известным происхождением, соответствующие рецепту. При отсутствии подходящего файла — честный placeholder/иллюстрация, не выдуманная фотография результата.
- Анимация короткая и функциональная: раскрытие, смена состояния, подтверждение выбора. Без задержек ради эффекта; `prefers-reduced-motion` обязателен.

### Альтернатива B — «Кулинарный журнал»

Для сравнения сделай только главную и меню: те же бренд и натуральная палитра, но более редакционная композиция, крупнее еда, меньше контейнеров. Это должна быть другая композиция, не простая перекраска A.

Покажи сравнение A/B, обоснуй выбор по требованиям, затем **самостоятельно продолжи A как основную реализацию**, если нет конкретного противоречия. Не жди отдельного выбора владельца для каждого отступа. B не превращай во второй полный продукт.

## 9. Telegram-специфика и доступность

Проектируй Mini App, а не просто сжатый desktop-сайт.

- Проверить ширины 320, 390, 430, 768 и 1280px. Нет горизонтальной прокрутки, обрезанных длинных русских названий и действий под нижней панелью.
- Учесть `safeAreaInset`, `contentSafeAreaInset`, `viewportStableHeight`, изменение размеров и открытие клавиатуры. Системные и Telegram safe areas — разные источники; не складывай их слепо и не ограничивайся одним `env(safe-area-inset-bottom)`.
- Уважать тему Telegram, сохраняя бренд: основной светлый вариант и читаемый резервный тёмный набор, а не случайная инверсия цветов. SDK-методы — с проверкой наличия/версии.
- Native BackButton возвращает по реальному локальному стеку и не теряет черновик. Не заменять «назад» выходом на первый экран во всех случаях. Обработчики SDK корректно снимаются.
- Избегать двух конкурирующих CTA: собственная fixed-кнопка и Telegram MainButton не должны одновременно перекрывать/дублировать действие.
- Нажимаемые области минимум 44×44px — требование этого продукта, не утверждение, что это минимум WCAG AA. Контраст обычного текста целевой не ниже 4.5:1; фокус, label, клавиатура, screen reader, reduced motion — проверяемые состояния.
- Haptic только для осмысленного действия и только если поддерживается. Не имитировать подтверждённую доставку «успешной» вибрацией.
- Browser preview, эмуляция устройства и настоящий Telegram Android/iOS/Desktop — разные проверки. Не подписывай browser screenshot как «проверено в Telegram».

Официальная техническая справка: https://core.telegram.org/bots/webapps . Сверяй актуальные поля/события, не выдумывай SDK API.

## 10. Техническая переносимость и границы интеграции

Основной проект сохраняет React/Vite + Python/FastAPI/SQLite/python-telegram-bot. Argon-песочница сейчас использует React 19/Tailwind 4/Express; это не разрешение мигрировать основной стек.

- Основной UI-пакет делай на переносимых React-компонентах: props/callbacks, CSS variables, минимум привязки к серверу или конкретной версии Tailwind. Не требуй нового глобального state-manager, дизайнера-конструктора или Express-сервера для переноса карточки.
- Не использовать API только React 19 в экспортируемых компонентах. Не переносить `@theme`/новые утилиты Tailwind 4 в Tailwind 3 без отдельного адаптера. Не устанавливать в основной проект новую motion-библиотеку ради пары переходов.
- Не переименовывать доменные поля ради UI. Из прочитанного основного контракта: `Recipe.id` — строка, `DayMenu.slots` — `Record<string, string>` (идентификаторы, не вложенные рецепты), `GeneratedMenu.created` — число. Перепроверь актуальные определения перед экспортом адаптеров.
- Текущий `Recipe` основного проекта ещё имеет числовые нутриенты; это не разрешение кодировать неизвестное нулём. Для демонстрационного UI используй отдельную view model с явным статусом неизвестных полей; изменение production DTO — задача интегратора.
- Выдели точки `onChooseMenu`, `onReplaceRecipe`, `onUpdateShopping`, `onSaveDiaryEntry`, `onOpenSupport`, `onRequestAccess`. Опиши вход/выход и статус демонстрации. Не реализуй их скрытыми платными/сетевыми вызовами.
- Все расчёты питания production — только через согласованный, покрытый тестами `src/core/keto-engine/`. Наличие твоих unit tests не утверждает медицинскую корректность и не разрешает перенос текущих формул.

## 11. Последовательность работы — ограниченная, без бесконечных переделок

### Этап A. Войти в контекст

Прочитай этот документ, доступные первичные требования и существующий код. Ответь коротко: что сохраняешь, что исключаешь, где нет доступа, где demo, где планируется реальная интеграция. Если сохранение создаёт remote-write, разреши только этот вопрос до правок. Не выдавай ещё один многостраничный roadmap вместо результата.

### Этап B. Найти композицию

Сделай A/B для «Сегодня» и «Меню», сравни с исходным референсом. Выбери A согласно заданию и объясни выбор. Не используй название KetoPulse и медицинский dashboard как стартовый шаблон.

### Этап C. Собрать полный путь

Реализуй основное направление A в своей изолированной рабочей области, переиспользуя компоненты. Должны работать переходы, синтетические локальные действия, возврат и ключевые пустые/ошибочные состояния. Не переписывай backend, не жди реальных токенов.

### Этап D. Проверить и один раз исправить

1. Прочитай `package.json` и запускай действительно существующие команды. Не называй `npm run lint` ESLint-проверкой, если это только `tsc --noEmit`.
2. Выполни сборку/типизацию и доступные UI-тесты в своей среде, если это не запускает реальные сервисы. Перед запуском проверь побочные эффекты команд.
3. В браузере пройди путь от начала до поддержки на синтетических данных; проверь возврат к анкете и сохранность черновика.
4. На всех заданных ширинах измерь overflow и видимость основных действий. На 320px отдельно проверь длинные русские названия; с клавиатурой — нижние кнопки и input.
5. Проверь пустой дневник, отсутствие подходящих блюд и недоступную поддержку/сеть. Ни один сценарий не должен показывать ложный успех.
6. Покажи реальные screenshots: мобильные «Сегодня», «Меню», «Рецепт», «Покупки», «Дневник», «Поддержка»; desktop — «Сегодня», «Меню», «Покупки». Снимки должны соответствовать последнему коду и иметь viewport/ref.
7. Сделай одну самопроверку композиции, типографики, контраста и излишней декоративности; затем один ограниченный цикл исправлений. Если остаётся blocker, назови его, не начинай третью полную концепцию.

## 12. Пакет сдачи и приёмка

Подготовь в своей рабочей области:

- `DESIGN.md` — палитра, типографика, spacing, компоненты, состояния, правила темы и Telegram-safe-area. Нормативные токены и объяснения должны совпадать.
- переносимые UI-компоненты, локальные assets, явные demo-fixtures; приложение открывается в preview без реального токена;
- `docs/design/flows.md` — маршруты и состояния каждого обязательного экрана;
- `docs/design/assets.md` — происхождение/права/статус изображений;
- `docs/design/integration.md` — переносимые файлы, зависимости, props/callbacks, mapping старых контрактов, что не интегрировано;
- `docs/design/verification.md` — точные команды, exit codes, проверки и ограничения; для screenshots — ref/viewport. Не подменяй запуск теста его описанием;
- `docs/design/screenshots/` — реальные снимки последнего прототипа;
- краткий список отличий от исходного визуала: что сохраняется и почему изменено остальное.

Критерии приёмки:

- [ ] Бренд «Кето Баланс», русский интерфейс, узнаваемый натуральный стиль; не новый спортивно-медицинский SaaS.
- [ ] Весь основной путь кликабелен; главный следующий шаг понятен без объяснения автора.
- [ ] Поддержка доступна до анкеты, возврат сохраняет черновик; канал не заменяет личную поддержку.
- [ ] Пустые записи действительно пустые; неизвестные данные не выдуманы; demo постоянно обозначено.
- [ ] Нет индивидуальных норм, электролитных доз, голодания/GKI/медицинских обещаний и фиктивных сообщений.
- [ ] Доступность, мобильные края, клавиатура и тёмный fallback проверены в обозначенном объёме.
- [ ] Экспорт не требует замены основного backend/стека и не ломает известные доменные контракты.
- [ ] Проверки приложены фактическими результатами; неподтверждённое честно указано.
- [ ] Основной репозиторий, production, реальные пользователи и секреты не затронуты; remote-write в песочнице выполнялся только при отдельном согласовании.
- [ ] Нет заявления «Telegram-релиз готов»: этот этап принимается как **дизайн-прототип и UI-пакет**, а не production.

Первое сообщение после чтения — короткое подтверждение контекста и точной рабочей области. Финальное — открываемый результат, screenshots, проверенные факты и integration handoff, а не обещание «готов продолжить».
