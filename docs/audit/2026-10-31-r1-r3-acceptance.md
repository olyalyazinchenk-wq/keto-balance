### R2 — свежий browser bundle, обе разновидности отметок

Повторена исходная последовательность: A+ → B+ при задержанном первом PUT → завершение первого PUT → A− при задержанном втором PUT → завершение оставшихся записей.

Отдельно проверены `checkedInStore` и `alreadyHave`. В обоих случаях:

- после старого completion отметка B остаётся true;
- окончательные A=false, B=true совпадают с намерением пользователя;
- UI и новый browser context показывают те же значения;
- все shopping PUT возвращают 200 с последовательными CAS-revisions;
- точные payload, записанные из браузера, воспроизведены на настоящем неизменённом in-process backend/SQLite; новая авторизованная сессия читает A=false, B=true.

Прежний сценарий добавления своего продукта во время refresh также проходит: продукт виден до и после = 1/1, shopping PUT 200, присутствует в transport store.

Browser transport использует private route fixtures и abort внешних запросов. Это реальное выполнение свежего JS/CSS в Chromium, но не утверждение, что browser и настоящий backend в этом прогоне были соединены HTTP-сервером: backend replay выполнен отдельно.

### R3 — ненулевая ревизия при bootstrap repair

Существующий синтетический профиль/меню с user revision=4: первый repair PUT содержит `expected_revision=4`, получает HTTP 200; unhandled rejections нет. Прежнюю ошибку `expected_revision=0 → 409` считать закрытой в этом воспроизведении.

## Неблокирующее замечание к отчётности исполнителя

`docs/release/evidence/k2-pilot-receipt.json` сейчас **невалиден как целый JSON**: `Extra data: line 61 column 5 (char 3560)`. После завершённого корневого документа остался старый блок E2E. Поэтому утверждение «все манифесты приведены в соответствие» не полностью верно.

Исполнителю следует перегенерировать эту квитанцию из фактических результатов без старого хвоста и проверить полным JSON parser, не только чтением первого объекта. Продуктовые файлы для этого менять не требуется. Это не отменяет независимые зелёные прогоны и **не блокирует согласованный локальный показ А**. Корректная независимая JSON-квитанция этой проверки сохранена отдельно в `evidence/r1-r3-acceptance-2026-10-31/checks.json`.

## Следующий шаг без новой инфраструктуры

Достаточно отдельного разрешения владельца: **«Запускай ознакомительный локальный показ А: loopback, отдельная синтетическая база, без бота, токенов, туннеля и реальных сообщений»**.

Перед запуском проверить, свободен ли выбранный порт; не останавливать чужие процессы и не занимать зарезервированные порты. После запуска проверить фактическую страницу и текущий build ID, затем пройти глазами настройки → меню → рецепт → покупки → reload. Не выдавать этот следующий операционный шаг за уже выполненный.
