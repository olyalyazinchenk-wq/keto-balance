## R1 — новый validator путает правильные и неправильные списки

**Место:** `bot/catalog.py:88–94,122–142`; применение к чтению/записи `bot/server.py:307–314,335–345`.

Причины:

1. `menu_recipe_ids` — set: повторные появления одного рецепта в разные дни теряются. Frontend `rebuildShoppingFromMenu` суммирует каждое появление (`src/ui/food-first/shoppingFromMenu.ts:110–146`).
2. `parse_amount_value` извлекает число, но не нормализует единицы (`bot/catalog.py:63–77`). Frontend нормализует г/кг и мл/л и форматирует итог (`shoppingFromMenu.ts:12–65`).
3. Цикл проверяет только присутствующие строки покупок, не полный набор обязательных ингредиентов. Удалённый ингредиент может остаться незамеченным.

### Фактически выполнено через helper → HTTP → SQLite → новая сессия

Входы сохранены в `consistency-inputs.json`. Для основных сценариев меню и количества получены **текущими оригинальными** `createMenuController`, `toRecipeViewModel`, `rebuildShoppingFromMenu`, не вычислены вручную и не взяты из медицинских данных. Для теста единиц есть отдельно помеченная синтетическая recipe fixture.

## R2 — новые ID сохраняются, более новые поля существующих ID теряются

**Место:** `src/PilotApp.tsx:533–543`. После завершения старого PUT за основу берётся `nextItems`; из актуального `shoppingItemsRef.current` добавляются только отсутствующие ID. Более свежие `checkedInStore`/`alreadyHave` для уже имеющихся ID заменяются старым снимком.

Предыдущий конкретный сценарий «добавить свой продукт во время refresh» **теперь проходит**; не возвращать его как неисправленный. Но заявленная защита чекбоксов не полна.

### Детерминированный браузерный сценарий на свежем bundle

Обозначения A/B — две реальные строки синтетического списка:

1. Отметить A; задержать первый shopping PUT.
2. Отметить B, пока первый PUT ожидает. На экране A=true, B=true.
3. Завершить первый PUT, задержать второй. Старое completion делает на экране A=true, **B=false**, хотя B пользователь не снимал.
4. Теперь пользователь снимает A. Третий snapshot уже содержит A=false, **B=false**.
5. Завершить оставшиеся запросы. Все три shopping PUT получают 200, CAS preconditions идут 2→3→4.
6. Ожидалось A=false, **B=true**. Фактически A=false, **B=false** на экране, в transport store и при новом browser context.

Браузерные payload не синтезировались вручную: сохранены в `queued-checkbox-payloads.json`, затем в том же порядке приняты настоящим неизменённым in-process backend/SQLite. Новая авторизованная сессия прочитала **A=false, B=false**, при всех HTTP 200. Это потеря намерения пользователя, а не один мерцающий кадр. Доказательства: `ui-probes.json` → `queued_checkbox_interleaving`, `r2-real-backend-replay.json`.
