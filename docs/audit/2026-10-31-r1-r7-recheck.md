## F1. Закончить единый допуск и обработку недостаточного каталога

**Source:** `src/PilotApp.tsx:432–442`, `src/adapters/pilotState.ts:75–85`, `src/ui/food-first/state.ts:176–184`, `FoodFirstApp.tsx:125–130,155–170,269–270,326–335`.

Callback замены всё ещё не использует replacement controller и не проверяет режим; predicate сам по себе режим профиля не обеспечивает. Detail по изменению hash проверяет наличие ID, а не ограничения профиля. Picker реконструирует canonical record из локального RECIPES, а не из загруженного catalog. Применить один controller/валидатор admitted pool + mode + restrictions/time + отсутствие повтора для generation/replacement/restored menu/detail; не полагаться на один UI picker. GET сохранённого state на сервере также не должен объявлять отозванные IDs действующими.

`PilotApp.tsx:300–305` генерирует меню **до try**, rebuild `:469–493` тоже без catch. Восстановление отсутствующего menu `:211–215` всё ещё генерирует 3 дня, игнорируя сохранённый planDays=1/7.

**Воспроизведено:** actual built bundle ab8… в частном браузере, synthetic empty catalog, подтверждение 18+, submit → unhandled rejection «Набор допущенных рецептов не утверждён или повреждён», форма остаётся на месте, PUT=0. Это адаптированный UI failure-path test с mocked transport, не доказательство настоящего сервера/Telegram.

**Приёмка:** понятный видимый отказ empty/insufficient/revoked/unsupported, без unhandled rejection и без ослабления ограничений; все варианты сохранённого planDays соблюдаются. Tests режима/исключения через callback и hash, а не только pure predicate.

## F2. Закончить составные сохранения и устойчивый conflict/error

**Source:** `PilotApp.tsx:307–337,355–410,527–584`.

Refresh поменял порядок, но обходит общую очередь и снимает локальный stale до подтверждения user PUT. Submit settings сохраняет state с stale=false прежде shopping PUT. Batches сохраняются двумя независимыми задачами. Любой поздний успех другого ресурса переписывает общий status в saved; catch убирает unhandled rejection, но не восстанавливает отказавшую запись.

**Воспроизведено на actual bundle в адаптированном UI test:** user PUT=409 → видим «Конфликт версий. Обновите страницу»; затем shopping PUT=200 → баннер меняется на «Тестовый каталог · синтетические данные». Неуспешное user-изменение не было исправлено, но предупреждение исчезло.

**Приёмка:** единая последовательность операций submit/batches/refresh без обхода очереди; stale остаётся до подтверждения нужных сохранений; partial failure не превращается в «актуально» после reload или в UI. Conflict/error сохраняются до явного reload/retry/reconcile именно отказавшего изменения. Не делать force overwrite и новый offline engine. Добавить browser cases 409 и network failure на втором save.

## F3. Исправить проверку версии и оставшуюся изоляцию

`bot/server.py:85–106` теперь фиксирует startup hash — это улучшение, но считает только bytes. `scripts/stamp-release.mjs:47–57` считает filename+bytes. Алгоритмы различны.

**Реальный in-process GET /api/version:** HTTP 200, backendFingerprint=`a607f3bd5622c5a6`, тогда как свежий build/manifest ожидает `56991253d8ffe96a`. Один и тот же исходник не проходит собственную проверку идентичности. Нужен один детерминированный формат и тест equality + stale-process/mutated-release проверки. Runbook также всё ещё содержит старые b184…/5b58… и старые счётчики.

`pilot_io_guard.py:58` намеренно исключает `.env.example` из запрета. Pure synthetic path probe показывает allowed=true вне run root; файл **не читался reviewer**. Это противоречит явному scope исходного ТЗ. Перенести тест документации из реального `.env.example` на synthetic fixture, убрать исключение, не ослаблять guard ради full discovery. После этого полный backend/gate можно безопасно повторять. Unit network guard по-прежнему не должен разрешать весь loopback кроме пяти портов: только нужный stdlib self-pipe, а у E2E свой test origin.

## F4. Подготовить запускаемый показ, не только текст согласования

Запрет публиковать лабораторный synthetic-key server теперь записан правильно. Но в `scripts/`/`bot/` не найден реализованный staging launcher с owner allowlist и таймером 1 час; в server/AppSettings такой механизм не подключён. Поэтому вариант Б — пока предложение, не готовая команда запуска. Подготовка кода и isolated synthetic tests допустима локально; реальные ключи/туннель/изменение кнопки/отправки требуют отдельного разрешения.

Вариант А тоже не является готовым пользовательским входом одним URL: PilotApp требует initData, а laboratory startup не создаёт browser identity. **Адаптированный browser probe без identity показывает «Требуется авторизация», API calls=0.** Нельзя просто предложить Ольге открыть localhost и ожидать онбординг. Если нужен локальный preview, предоставить изолированный явно demo-only bootstrap с синтетической identity, не guest bypass в продукте.

**Приёмка подготовки:** конкретная команда owner-only staging, явно переданные immutable artifact/catalog/temp DB, real-key configuration только доверенным локальным способом после согласования, allowlist после HMAC и до персональных записей, платежи off, ограниченное время жизни, собственные process handles/teardown. Synthetic тесты допуска/отказа не-владельцу и истечения времени. Не переносить fake-key endpoint в публичный запуск. Состав пяти кандидатов и [УТОЧНИТЬ] сохраняются; это не approval медицинских данных или production-рецептов.

После локальных F1–F4 — **один конкретный запрос** на включение подготовленного режима и реальная личная приёмка Telegram. Не повторять продуктовый выбор/интервью, не расширять функции, не просить продолжать после обычной разрешённой локальной правки.
