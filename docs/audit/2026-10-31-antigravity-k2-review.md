## P0 — аутентификация обходится на уровне HTTP-маршрутов

`bot/auth.py:75–97` содержит HMAC-сравнение и проверки времени. Но наличие правильной функции не гарантирует, что каждый пользовательский маршрут её требует.

### Обход 1: идентификатор пользователя считается доказательством личности

`bot/server.py:82–111`: `extract_authenticated_user_id` при отсутствии Bearer-сессии возвращает присланный `query_user_id` или `x_user_id` (`104–105`). `allow_anonymous_preview=False` этот путь не закрывает.

Прямое последствие относится к профилю, покупкам и data-rights handlers, которые пользуются той же функцией (`218–264`, `325–345`). Live пользовательские API не проверялись и реальные данные не читались.

### Обход 2: тестовые строки создают сессию без подписи

`bot/server.py:173–204`: если строка initData имеет тестовый prefix/marker, проверка HMAC пропускается даже при непустом настроенном signing key. Далее из неё принимается user_id и выдаётся сессия. Отдельный `app_stage`/strict production guard этот путь не ограничивает. При отсутствии токена также есть гостевой путь.

### Поведенческое доказательство

Фабрика `create_app` запущена **только в TestClient**, с новой БД в Hermes scratch, явно заданными `app_stage='production'`, `allow_anonymous_preview=False` и непустым **синтетическим** signing key. Фиктивный пользователь/профиль созданы только в этой БД.

| Проверка | Получено | Требуемая граница |
|---|---|---|
| Нет identity вообще | 401 | Контрольный отрицательный случай работает |
| Нет сессии, только user_id в query | 200, получен fake профиль | 401/403 |
| Нет сессии, только X-User-Id | 200, получен fake профиль | 401/403 |
| Неподписанная test/mock initData | 200, создана сессия fake пользователя | Отказ |
| Полученная таким образом сессия читает fake профиль | 200 | Такая сессия не должна существовать |

Реальные env/БД/runtime JSON и внешняя сеть запрещались audit hook в этой пробе. Счётчик запрещённых попыток I/O пуст. Session tokens и настоящие секреты в evidence не выводились. Это доказательство дефекта авторизации на синтетике, **не утверждение об утечке или эксплуатации настоящих данных**.

**Узкое исправление:** личность только из проверенной сессии/Telegram initData; query/header IDs не являются авторизацией. Все test bypass должны быть вне production request path — через injectable test fixtures, не magic strings. Отсутствие signing key не должно включать авторизацию по умолчанию. Добавить негативные route-level regression tests на оба класса обхода, сохранить signed-user isolation controls. Пока этого нет, не подключать данные участников.

## Следующий результат вместо бесконечного расширения

1. Сначала закрыть два auth bypass и добавить route-negative tests. Не предлагать новые функции или тарифы.
2. Назначить одного release owner. Соединить минимальный настоящий поток: Telegram session → собственный профиль/настройки → owner-допущенный каталог → меню → покупки → сохранение и восстановление. Не обходить controller/rules ради визуального экрана.
3. Для первого ограниченного показа можно отдельно опубликовать честный preview без личных данных после S-PUBLISH. Не обещать ему server sync. Для полезного K2 нужен согласованный frontend+backend staging, а не один static dist.
4. Финальная приёмка — владелец открывает конкретную проверенную сборку через реальный Telegram-вход, проходит полезный сценарий, повторно открывает его с сохранёнными данными. Фактическую поддержку проверить отдельным согласованным nonsensitive сообщением. До этого K1/K2 не выдавать за принятые.

Предыдущие конкретные guard-замечания не переносятся автоматически: `vite.config.ts:6` теперь содержит изолированный envDir, `scripts/verification.py:226` снова удаляет PYTHONPATH. Полный build lifecycle здесь не повторялся, поэтому это наблюдение об исправленном коде, не новый безусловный I05 PASS.
