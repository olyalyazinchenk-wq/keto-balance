# TEAMWORK — Протокол совместной работы и координации агентов

Настоящий протокол определяет правила согласованной работы агентов и разработчиков в репозитории `C:\Users\HP\Keto-balance`.
Протокол действует совместно с `AGENTS.md`. При любых расхождениях безусловный приоритет имеют инварианты `AGENTS.md`.

---

## 1. Базовые правила координации и роли

1. **Иерархия документов**: `AGENTS.md` задаёт фундаментальные ограничения; `docs/LIVE_STATUS.md` описывает текущее оперативное состояние; `docs/release/release-plan.md` содержит единый рабочий бэклог выпуска.
2. **Функциональные роли, а не названия моделей**:
   | Роль | Ответственность | Зона файлов | Ограничения |
   |---|---|---|---|
   | **Координатор** | Критический путь, бэклог, распределение задач, интеграция, отчёт | `docs/release/release-plan.md`, координационные документы | Не подменяет проверки заявлениями исполнителей |
   | **Исполнитель A** | Бэкенд, данные, платежи, эксплуатация | `bot/server.py`, `bot/app_db.py`, `bot/payments.py`, `bot/app_settings.py`, `deploy/*` | Единственный автор общих серверных контрактов |
   | **Исполнитель B** | Интерфейс, контентный процесс, пользовательские сценарии | `src/PilotApp.tsx`, `src/ui/*`, `src/tma/*`, `src/data/*` | Работает строго по зафиксированным контрактам |
   | **Независимый проверяющий** | Отрицательные сценарии, воспроизведение дефектов, приёмка | `tests/*`, `scripts/verification.py` | Не редактирует проверяемую реализацию |
3. **Правило одного писателя (Single Writer Rule)**: В один момент времени один файл изменяет ровно один назначенный исполнитель. Общие `bot/server.py`, `bot/app_db.py`, `src/PilotApp.tsx` и `scripts/verification.py` закреплены строго за своими авторами.
4. **Контроль исходного состояния**: Перед правкой исполнитель сравнивает файл с сохранённым baseline (`git status --short`). Неожиданное изменение требует согласования, а не перезаписи чужих правок.
5. **Новый сценарий через TDD**: Для каждого существенного сценария: воспроизводимый RED → минимальная реализация → GREEN → релевантная регрессия.
6. **Правила повторного тестирования**: Проверяющий воспроизводит релевантные проверки. Новый полный прогон (включая E2E) выполняется при изменении кода или при обнаружении дефекта, требующего подтверждения исправления.
7. **Канонические статусы задач**: `подготовка`, `в работе`, `блокер`, `локально проверено`, `передано`.
8. **Обработка дефектов**: Обнаруженный дефект возвращается ответственному исполнителю. Проверка повторяется после устранения причины.

## 2. Процессная и сетевая безопасность

1. **Неприкосновенность системных портов**:
   - Категорически запрещено останавливать или перезапускать процессы на портах:
     - `8000` (FastAPI / бот)
     - `4387` (Vite)
     - `8090` (студия НутриОК)
     - `10808 / 10809` (прокси)
2. **Управление локальным показом (порт 18080)**:
   - Если порт `18080` занят посторонним процессом, **запрещено** останавливать его по совпадению имени программы (`python.exe` и т.д.); необходимо зафиксировать блокер.
   - Остановить разрешается **только** процесс, запущенный текущим исполнителем в рамках данной сессии/задачи (по сохранённому PID/handle).
   - Превью для владельца запускается через `scripts/run_local_preview.py` строго с указанием параметров изолированной сборки.

## 3. Дисциплина Git и релизная ветка

1. **Авторизованный Git-процесс**:
   - Владельцем прямо авторизована работа в ветке `release/1.0.0`.
   - Разрешены адресные атомарные коммиты (`feat(...)`, `fix(...)`, `docs(...)`, `test(...)`), push ветки `release/1.0.0` и открытие Pull Request.
   - Категорически запрещены `git add .`, `git reset --hard`, `git clean -fd`, `git checkout .`.
   - Прямой push в `master`, слияние релизной ветки и развёртывание в production производятся только после личного подтверждения владельца.
2. **Контур НутриОК (`C:\Users\HP\Desktop\Новая папка`)**:
   - Не входит в данный релиз Keto Balance. В рамках данного задания изменений не вносить.

## 4. Критерии готовности этапа (Definition of Done)

Этап считается завершённым только при одновременном выполнении условий:
1. Все приёмочные команды выполнены, и в отчёте приведён их фактический вывод с кодом завершения.
2. Проведены модульные, интеграционные и сквозные проверки (Playwright E2E строго с `--config=playwright.full.config.ts`).
3. Создан воспроизводимый изолированный дистрибутив (`Build ID` зафиксирован).
4. Зафиксированы актуальные хеши артефактов и схемы БД.
5. Честно задокументированы все ограничения, пометки `[УТОЧНИТЬ]` и блокеры.
6. Файл `docs/LIVE_STATUS.md` актуализирован.
