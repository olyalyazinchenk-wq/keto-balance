# Первый видимый результат в Telegram — релизный слот

**Статус:** решение для согласования, не разрешение на реальные отправки, рестарты, публикацию или расходы. Составлено 30 октября 2026 года по проверке около 14:30 МСК.

**Goal:** показать владельцу один реально исполняемый сценарий в существующем Telegram-боте, а не ещё один локальный отчёт.

**Architecture:** первый показ — существующий бесплатный нативный диалог НутриОК в уже работающем WellnessBot; для него не нужны новый Mini App, входящий HTTPS-туннель или большой рефакторинг. Новый интерфейс «Кето Баланс» остаётся отдельной проверяемой линией: его показ в Telegram требует одобренного внешнего HTTPS-входа, а перенос в основной продукт — отдельной интеграции. Не объединять автоматически репозитории, бренды, тарифы и данные.

**Tech Stack:** существующий WellnessBot/aiogram/Windows Scheduled Task; существующий React-прототип Keto Balance. Новые модели, профили, MCP и серверы не являются условием первого нативного показа.

## 2. Суть проблемы

Работа идёт, но результаты частей не сведены в один подтверждённый пользовательский вход. Готовность локального интерфейса, Git-синхронизация, количество тестов и запущенный процесс принимаются отдельно; фактическое открытие нужного результата владельцем остаётся без владельца релизной задачи.

Дополнительный конкретный разрыв: новый UI, обслуживаемый backend и адрес туннеля относятся к разным артефактам/этапам. Поэтому новая локальная работа сама не появляется за существующей кнопкой Telegram.

Не установлены в этом ходе: качество полного paid-report pipeline, соответствие live Bot API identity локальной конфигурации, актуальное содержимое кнопки Mini App и возможность непрерывной круглосуточной работы. Не объявлять их готовыми.

Владелец открывает существующего `@zinchenko_wellness_ai_1_bot` в настоящем Telegram и на разрешённом тестовом аккаунте проходит:

**Начать → «ОК-Старт — бесплатно» → необходимые подтверждения → цель → исходная оценка → ответ «ОК-Старт завершён» с первым шагом.**

Это ограниченный работающий бесплатный сценарий, НЕ полный B7, НЕ платный отчёт и НЕ новый food-first Mini App.

Кодовые ориентиры для исполнителя:

- `C:/Users/HP/Desktop/Новая папка/WellnessBot/main.py:306–323` — бесплатный формат в клавиатурах;
- `main.py:3038–3043` — `/start` отправляет меню; **он также очищает текущую сессию**;
- `WellnessBot/handlers/nutriok_intake.py:494–548` — baseline и завершение ok_start; видимая ветка формирует ответ без запуска генерации PDF;

Не использовать `/start` поверх незавершённой рабочей анкеты. Нужен чистый тестовый аккаунт либо осознанное разрешение владельца сбросить только его собственную тестовую сессию.

## 4. Один ответственный, ограничение незавершённой работы

- Runtime-исполнитель TG0: действующий Antigravity, работающий в каноническом WellnessBot workspace и отвечающий за Scheduled Task. Конкретная модель не меняет обязанности довести до пользовательского ответа.
- Архитектор/приёмка: текущий управляющий контекст; принимает реальный показ, а не самоотчёт исполнителя.
- UI-исполнитель Keto: сохраняет текущий принятый прототип и исправляет только согласованные дефекты. Не управляет параллельно WellnessBot runtime.
- Reviewer — read-only. Не пишет в те же файлы вторым исполнителем.

**Предлагаемая пауза до TG0:** не начинать большой спринт C по разбиению main.py, миграцию БД, новые офферы, новые дизайн-концепции, интеграции памяти и установку новых skills. Срочная безопасность не отменяется. Это предлагаемая организационная договорённость, не уже применённая техническая блокировка работников.

## 6. Малые действия исполнителя в TG0

Каждый пункт — примерно 2–5 минут сосредоточенной работы; Telegram-действия/ожидание владельца отдельно.

1. Зафиксировать workspace, branch, HEAD и единственного runtime owner. Не начинать копию или второй poller.
2. Согласовать чистую тестовую сессию и границы десяти действий пользователя; не выбирать платный формат.
3. Владелец/уполномоченный тестировщик открывает конкретный чат. Записать время первого действия. Публичной страницы недостаточно.
4. Нажать «Начать» и проверить реальное появление двух ожидаемых сообщений/клавиатур.
5. Выбрать бесплатный ОК-Старт, пройти обязательные подтверждения, цель и тестовую исходную оценку. Не вводить реальную историю болезни или данные клиента.
6. Проверить реальное завершение короткого сценария и ответ, не просто сохранённую локальную запись.
7. При ошибке зафиксировать **первый** сломанный переход: бот не отвечает / нет кнопки / callback не обрабатывается / состояние теряется. Исправлять только его. Для кода — RED/GREEN и узкая регрессия; при допустимом рестарте только Scheduled Task WellnessBot, не отдельный Python.
8. Сдать один короткий результат: bot username, HEAD, время, пройденные шаги, обезличенные скриншоты именно чата и подтверждение владельца. Если не прошли — FAIL с конкретной границей, без «в целом всё готово».

Не выполнять реальные paid/stt/LLM/PDF вызовы в TG0. Не читать пользовательские кейсы/полные runtime logs для доказательства. Если нужна диагностика, использовать разрешённую обезличенную метаинформацию тестового прохода.

## 7. Новый Keto UI: убрать зависимость просмотра от сломанного сохранённого туннеля

После TG0 — один выбранный путь: публикация только очищенной статической demo-сборки food-first на согласованном HTTPS-хостинге, например Cloudflare Pages Direct Upload, с проверкой нулевых расходов. Это предложение, доступ к такому аккаунту не подтверждён.

Предпосылки: разрешение владельца на внешнюю публикацию, конкретный аккаунт/доступ, проверенный allowlist файлов, согласованный bot/test-entry. Если их нет, оценка 2–4 часа ещё не начинается.

- Не публиковать source workspace, public/assets/aistudio с приватными планами, .env, данные участников и backend.
- Не считать непубличный URL защитой. Без проверенной авторизации обычный Pages URL общедоступен; допустим только явно согласованный demo с synthetic data.
- Не менять production-кнопки и не включать ENABLE_TMA в WellnessBot без отдельного решения. Не подменять его текущий продукт другим интерфейсом.
- Проверить внешний HTTPS из независимого клиента, фактические JS/CSS/build marker, затем открытие в настоящем Telegram. Скриншот localhost не заменяет это.
- Не называть статический demo принятым M0 основного Keto с реальной поддержкой, backend или нормализацией покупок.
- Сервер на ПК для первого владельческого показа не означает 24/7. Круглосуточное размещение — отдельный этап, не автоматически оплачиваемый VPS.

Ранее опубликованная основная Keto-сборка и новый прототип сохраняются. Основной перенос требует существующих адаптерных контрактов и проверок; не копировать donor package.json/fixtures/domain stubs поверх основного продукта.

Первичный источник способа статической публикации: `https://developers.cloudflare.com/pages/get-started/direct-upload/` (проверен выдачей официального домена; прямое извлечение в этой среде получило 403). Установка CLI, публикация и проверка аккаунта не выполнены.

- Нет основания объединять проверки 23 и 93 в «общую готовность приложения».

## 9. Предлагаемый пакет согласия на следующий шаг

Разрешить **только TG0** в существующем боте: владелец/одобренный тестовый аккаунт, до десяти текстовых/кнопочных действий, синтетические значения, без платных вызовов, реальных клиентов, оплаты, рассылок, PDF и изменения тарифов. Один рестарт только существующей Scheduled Task — лишь при необходимости и отдельном включении в согласие. Секреты не передаются в чат и не выводятся; работа через уже настроенный сервис.

Публикация Keto demo/смена кнопки/новый хостинг в это согласие **не входят**. Не делать commit/push/deploy только на основании этого документа.

## 10. Критерий остановки

Успех — владелец сам увидел ожидаемый ответ существующего бота. Тогда TG0 закрывается и команда переходит к следующему отдельному результату.

Неуспех — по истечении контрольного слота нет ответа: фиксируется проверенный блокер с ответственным и следующим конкретным действием, не запускается очередной спринт «заодно». Никакой файл, тестовый счётчик, статус процесса или слово LGTM этот критерий не заменяет.
