# Инструкция по развёртыванию «КетоБаланс» на Linux (Cloud.ru Evolution / VPS)

Документ описывает процедуру безопасного развёртывания приложения в среде Linux (Ubuntu 22.04 / 24.04) с минимальным потреблением ресурсов (1 vCPU / 2 ГБ RAM) и нулевыми предварительными затратами (0 ₽).

---

## 1. Системные требования и архитектура

Стек спроектирован с жёстким лимитом памяти до **1.4 ГБ**, что гарантирует стабильную работу на виртуальном сервере **1 vCPU / 2 ГБ RAM** с запасом более 600 МБ для ядра Linux и системных служб.

| Компонент | Роль | Потребление RAM | Лимит RAM |
|---|---|---|---|
| **Caddy 2** | Обратный прокси, автоматический HTTPS (Let's Encrypt), сжатие zstd/gzip, CSP-заголовки | ~25–35 МБ | 200 МБ |
| **Web (FastAPI)** | REST API, выдача SPA-приложения, проверка подписи Telegram WebApp, вебхуки | ~120–160 МБ | 700 МБ |
| **Bot (aiogram / PTB)** | Фоновый опрос Telegram (long polling), команды меню, трекер воды, калькулятор БЖУ | ~80–110 МБ | 500 МБ |
| **SQLite (WAL)** | База данных пользователей, профилей и синхронизации (хранится в volume `keto_data`) | ~20–40 МБ | Общий с Web/Bot |

**ИТОГО:** фактическое потребление в спокойном состоянии — **~250–350 МБ RAM**. Пиковое при нагрузке — менее 700 МБ.

## 2. Подготовка перед запуском (Pre-flight)

### 2.1. Создание конфигурации `.env`
На сервере в корневой директории скопируйте шаблон:
```bash
cp .env.production.example .env
```
*(Также можно сохранить как `.env.production` и передавать флаг `--env-file .env.production` в Docker Compose).*

Заполните параметры:
- `WEBAPP_DOMAIN` — домен для HTTPS (например, `ketobalans.ru` или `app.ketobalans.ru`).
- `TELEGRAM_BOT_TOKEN` — токен бота от `@BotFather`.
- `TELEGRAM_WEBHOOK_SECRET_TOKEN` — произвольный случайный пароль для защиты вебхуков.
- `KETO_BOT_PROXY` — опционально: прокси при наличии сетевых ограничений к Telegram API.

> [!IMPORTANT]
> **Платежи по умолчанию строго отключены** (`PAYMENT_MODE=disabled`, `PAYMENTS_ENABLED=0`).
> Никакие реальные списания не происходят до явного разрешения владельца.

### 2.2. Проверка доступности Telegram API в дата-центре
В российских дата-центрах часть диапазонов IP Telegram может блокироваться или фильтроваться.
Выполните встроенный тест:
```bash
python3 scripts/check_telegram_access.py
```
- Если результат `[OK]` (`TELEGRAM_DIRECT_OK`): сервер свободно связывается с Telegram.
- Если результат `[WARNING]` (`TELEGRAM_BLOCKED_OR_UNREACHABLE`): укажите прокси в `.env` (или `.env.production`):
  ```env
  KETO_BOT_PROXY=http://proxy_user:proxy_password@proxy_host:proxy_port
  ```

## 3. Главная команда развёртывания

Развёртывание всего стека выполняется **одной командой**:

```bash
docker compose up -d --build
# Или при явном файле окружения: docker compose --env-file .env.production up -d --build
```

Команда автоматически:
1. Соберёт оптимизированный фронтенд в изолированном контейнере Node 20.
2. Создаст защищённый runtime-образ Python 3.12 без секретов и временных файлов.
3. Запустит Web-сервер, Telegram-бота и Caddy-прокси.
4. Выпустит бесплатный доверенный SSL-сертификат HTTPS через Let's Encrypt.

---

## 4. Проверка работоспособности (Healthcheck)

После выполнения команды проверьте статус сервисов:
```bash
# 1. Проверка состояния контейнеров
docker compose ps

# 2. Проверка здоровья локального бэкенда
curl -f http://127.0.0.1:8000/api/health

# 3. Проверка внешнего HTTPS-эндпоинта и версии сборки
curl -f https://<ВАШ_ДОМЕН>/api/version
```

Ожидаемый ответ:
```json
{"status":"ok","buildId":"...","catalogHash":"...","backendFingerprint":"..."}
```

## 5. Резервное копирование и восстановление

### Создание резервной копии:
```bash
./ops/backup-db.sh
```
*(Или вручную через Docker: `docker compose exec web python scripts/backup_db.py`)*.
Бэкап создаётся в WAL-безопасном режиме через SQLite Backup API, проверяет SHA256 и сохраняет метаданные в `.json`.

### Восстановление из копии:
```bash
./ops/restore-db.sh /app/data/backups/keto_balance_YYYYMMDD_HHMMSSZ.db
```
Скрипт проверяет контрольную сумму, останавливает поллер бота, восстанавливает БД, выполняет `PRAGMA integrity_check` и перезапускает сервисы.

## 6. Процедура отката (Rollback)

Если в новой версии обнаружена ошибка, откат к предыдущей стабильной версии выполняется **одной командой**:

```bash
git checkout <ХЭШ_ПРЕДЫДУЩЕГО_КОММИТА> && docker compose up -d --build
```

Если потребовался откат данных, восстановите соответствующий бэкап:
```bash
./ops/restore-db.sh /app/data/backups/<НУЖНЫЙ_СНАПШОТ>.db
```

## 7. Контроль тарифицируемых ресурсов и демонтаж (0 ₽)

При выводе сервера из эксплуатации или завершении использования гранта:
1. Запустите сухой прогон проверки бэкапа и готовности:
   ```bash
   python3 scripts/cloudru_teardown.py --backup-file /path/to/backup.db.enc --key-file /path/to/key
   ```
2. Выполните гарантированный ручной демонтаж всех ресурсов (VM, Boot Volume, Data Volumes, Floating IP, Snapshots, Buckets) строго по регламенту:
   [`docs/CLOUDRU_MANUAL_TEARDOWN.md`](../CLOUDRU_MANUAL_TEARDOWN.md).
