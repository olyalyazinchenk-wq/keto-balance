## Конкретное изменение, требующее разрешения

Рекомендуется разрешить **однократное закрытое обновление существующего приложения и бота с добавочной миграцией очереди**. Оно добавляет таблицу `support_reviews` и индекс, создаёт связи для существующих обращений, не меняет прежние таблицы и сохраняет меню и покупки. Потребуется короткая остановка двух контейнеров. Новых серверов, расходов, платежей, публичного выпуска и внешней обработки вопросов не будет.

После прямого согласия Ольги оператор создаёт на ВМ файл `owner-approval.json` с правами 600:

```json
{"approved_by":"Olga","build_id":"8be43f00ba6d26b3","scope":"private-owner-update-and-support-migration","approved_at":"Фактическая дата и ссылка на согласие"}
```

Это образец, а не полученное согласие. Файл ещё не создан. Затем оператор выполняет в закрытом каталоге:

```sh
sudo -n python3 owner_rollout_vm.py switch --approval-file owner-approval.json
```

Скрипт проверяет согласие, неизменность пакета/preflight, образ и прежние контейнеры; останавливает бот и приложение в защищённом блоке восстановления; сохраняет новые резервные копии; выключает автозапуск сохранённых старых контейнеров. Миграция выполняется внутри проверенного образа без сети. Новый бот получает тот же volume, новую общую очередь и прежнюю историческую базу. Порт app, Caddy, оба Xray и остальные проекты сохраняются.

Успех запуска бота проверяется по работающему контейнеру, отсутствию перезапусков и свежему heartbeat. Это ещё не доказательство polling: итоговая проверка Telegram выполняется отдельно, без тестовых сообщений клиентам. До неё receipt прямо помечает `telegram_polling=not verified`. Если запуск или heartbeat не подтвердятся, автоматически возвращаются прежние контейнеры.

## Откат и проверка после обновления

Ручной откат тем же оператором:

```sh
sudo -n python3 owner_rollout_vm.py rollback --approval-file owner-approval.json
```

Новые контейнеры останавливаются, их автозапуск выключается. Прежним контейнерам возвращаются имена и исходная restart policy. Одновременно два получателя Telegram не запускаются. Добавочная таблица остаётся; восстанавливать старую копию поверх актуальной базы не требуется. Исторический модуль использует тот же канонический файл с теми же WAL/SHM, поэтому свежие записи не остаются в слое контейнера.

После переключения оператор проверяет HTTPS `/api/version`, отсутствие второго polling-процесса, Telegram API через существующий выход, ошибки и перезапуски, актуальность резервных копий. Ольга открывает прежний бот с телефона и проходит личную приёмку. Затем начинается 24-часовое наблюдение. Репетиция и браузерные тесты не заменяют эти проверки.
