# Руководство по запуску и эксплуатации тестового пилота (Pilot Runbook)

## 1. Назначение и рамки безопасности
Данный документ регламентирует порядок локального запуска, проверки здоровья и безопасного отката рабочего пилота «Кето Баланс» (версия Wire v1, рубеж L2).

### Ключевые ограничения безопасности:
- **Никаких модификаций чужих портов:** Боевые и вспомогательные процессы на портах `8000`, `4387`, `8090`, `10808`, `10809` запрещено останавливать или перенаправлять без прямого указания.
- **Выделенный тестовый порт:** Локальный верификационный сервер использует строго `127.0.0.1:18080`.
- **Изоляция базы данных и каталога:** Все тестовые записи и временные SQLite БД создаются исключительно в изолированном scratch-каталоге `C:\Users\HP\AppData\Local\hermes\cache\scratch\`.
- **Секреты:** Никакие реальные токены Telegram-ботов, подписи `initData` или личные ключи не записываются в Git и не передаются в чат.

## 2. Локальный запуск верификационного сервера

### Шаг 1. Проверка окружения
Убедитесь, что используется изолированный виртуальный интерпретатор Python:
```powershell
cd C:\Users\HP\Keto-balance
& ".venv-p0/Scripts/python.exe" --version
```
*Ожидается:* Python 3.14.9 или совместимый.

### Шаг 2. Сборка изолированного артефакта
Сборка frontend осуществляется без перезаписи боевого каталога `dist/`:
```powershell
node scripts/build-isolated.mjs --serve-test --json
```
Команда собирает клиентский бандл во временную директорию, экспортирует синтетический тестовый каталог и генерирует `build-receipt.json` с фингерпринтами.

### Шаг 3. Запуск локального тестового сервера (порт 18080)

Для локального браузерного показа Ольге (Вариант А):
```powershell
& ".venv-p0/Scripts/python.exe" scripts/run_local_preview.py --port 18080
```
Сервер поднимает изолированный preview-контур и выводит готовый URL:
`http://127.0.0.1:18080/?demo_user=1084557944`
(Вход выполняется в один клик без Telegram WebApp, создаётся демо-сессия для ID `1084557944`, процесс автоматически завершается через 1 час).

Для owner-only staging показа через Telegram WebApp (Вариант Б):
```powershell
# Рекомендуемый доверенный способ: передача через локальный файл секрета или переменную окружения
& ".venv-p0/Scripts/python.exe" scripts/run_staging.py --port 18080 --token-file "path/to/token.txt"
# Или:
# $env:TELEGRAM_BOT_TOKEN="..."; & ".venv-p0/Scripts/python.exe" scripts/run_staging.py --port 18080
```
Сервер проверяет реальную подпись Telegram HMAC, допускает только ID `1084557944` (все остальные получают 403 до создания записей в БД), отключает платежи и автоматически завершает работу через 1 час. Никогда не передавайте реальный токен открытым текстом в параметрах argv командной строки.

### Шаг 4. Проверка здоровья (Health Check)
Выполните GET-запрос к эндпоинту версии:
```powershell
curl http://127.0.0.1:18080/api/version
```
*Ожидаемый ответ:*
```json
{
  "buildId": "c9774a016e0173e8",
  "backendFingerprint": "317b35e410187a94",
  "catalogHash": "face03d34bf329b2",
  "status": "ok"
}
```
Все три фингерпринта (`buildId`, `backendFingerprint`, `catalogHash`) совпадают со значениями в `docs/release/artifact-manifest.json` и `dist/release.json`.

## 4. Процедура остановки и отката (Rollback)

### Остановка тестового сервера
- Если сервер запущен в терминале, нажмите `Ctrl+C`.
- Если сервер запущен в фоновом режиме, останавливайте его строго по сохранённому PID (Process ID) собственного процесса, без слепого сканирования и завершения сторонних процессов по номеру порта.

### Очистка временных файлов
Все временные тестовые базы данных и сборки размещаются в каталоге:
`C:\Users\HP\AppData\Local\hermes\cache\scratch\`
Их удаление при необходимости производится только точечно в рамках собственного runId.

### Откат изменений кода (при необходимости)
Для инспекции состояния рабочей ветки используйте:
```powershell
git status
git diff
```
Никогда не выполняйте деструктивные команды `git restore .` или `git clean -fd` без явного решения владельца, так как они могут стереть необходимые артефакты и несохранённые доработки.

- Кнопка «Написать Ольге» формирует ссылку: `https://t.me/keto_balance_userbot?start=question`.
- При отправке текстового вопроса в форме обратной связи тикет сохраняется в базе данных бэкенда (`user_tickets`).

## 6. Производственное развёртывание и регламент резервного копирования (Release Candidate 1.0.0)

### 6.1. Развёртывание через Docker Compose
Производственный стек включает:
- Контейнер `backend`: Python 3.12, FastAPI, Uvicorn (2 воркера), автоматическая инициализация SQLite базы данных в `/data/keto_balance.db`.
- Контейнер `nginx`: Nginx reverse proxy, терминация HTTPS, gzip-сжатие, заголовки безопасности (CSP, Frame-Options), rate-limiting для биллинга (5 запросов в минуту) и долговременное кэширование статических ассетов (1 год, `immutable`).

Запуск на сервере Linux:
```bash
cd /opt/keto-balance
docker compose -f deploy/compose.yaml up -d --build
```

Проверка статуса:
```bash
docker compose -f deploy/compose.yaml ps
curl -f http://localhost/api/health
```

### 6.2. Регламент резервного копирования (SQLite WAL Backup)
Резервное копирование выполняется утилитой `scripts/backup_db.py`, использующей официальный SQLite Online Backup API. База данных копируется атомарно без остановки сервиса и без блокировки пишущих транзакций.

Запуск создания резервной копии:
```bash
python scripts/backup_db.py --source /data/keto_balance.db --dest /data/backups
```
Скрипт генерирует:
- Снапшот БД: `/data/backups/keto_balance_YYYYMMDD_HHMMSSZ.db`
- Метаданные с контрольной суммой SHA-256: `/data/backups/keto_balance_YYYYMMDD_HHMMSSZ.json`

Рекомендуемое расписание (crontab на хосте):
```cron
# Ежедневно в 03:00 UTC
0 3 * * * python /opt/keto-balance/scripts/backup_db.py --source /data/keto_balance.db --dest /data/backups >> /var/log/keto_backup.log 2>&1
```

### 6.3. Процедура аварийного восстановления (Disaster Recovery)
При повреждении или сбое диска восстановление выполняется строго по верифицированной контрольной сумме:
```bash
python scripts/restore_db.py /data/backups/keto_balance_YYYYMMDD_HHMMSSZ.db --target /data/keto_balance.db
```
Утилита:
1. Проверяет SHA-256 хэш файла бэкапа по метаданным `.json`.
2. Атомарно восстанавливает базу данных в целевой файл.
3. Запускает `PRAGMA integrity_check` и подтверждает статус `ok`.

### 6.4. Единый верификационный гейт
Перед публикацией любого релиза или обновлением контейнера запускается сквозной гейт:
```bash
python scripts/verification.py --stage public-paid
```
Гейт последовательно проверяет:
1. Полный backend-набор (167 тестов: аутентификация, CAS, платежи, права данных, вебхуки Stars).
2. Полный frontend-набор (193 юнит-теста).
3. Строгую проверку типов TypeScript (`tsc --noEmit`).
4. Изолированную сборку Vite и валидацию манифеста каталога.
5. Полный Playwright E2E сьют (11 браузерных сценариев).
