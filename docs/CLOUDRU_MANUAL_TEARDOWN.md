# Регламент полного ручного демонтажа ресурсов в личном кабинете Cloud.ru
## Гарантия 0 ₽ остаточных начислений при выводе сервиса из эксплуатации

Настоящий регламент является **официальной, обязательной и проверяемой процедурой** гарантированного вывода ресурсов из Cloud.ru Evolution без риска возникновения задолженности или списаний с карты после завершения пилота.

> [!WARNING]
> **Автоматическое удаление через API заблокировано в целях безопасности.**
> В облачных платформах Enterprise-уровня API-токены могут обладать ограниченной областью видимости или завершаться таймаутом, оставляя «осиротевшие» тарифицируемые диски или публичные IP.
> **Ручной демонтаж через веб-консоль Cloud.ru с визуальной сверкой всех разделов — единственный способ на 100% подтвердить нулевой остаточный баланс (0 ₽).**

## Этап 0: Предварительная защита данных (до удаления чего-либо)

Никакие ресурсы в облаке не удаляются, пока копия базы данных не проверена и не сохранена **вне удаляемого сервера**.

1. **Создание зашифрованной резервной копии на сервере:**
   ```bash
   # Генерация стойкого случайного ключа Fernet (если ещё не создан):
   python3 scripts/backup_db.py --generate-key-file /tmp/backup_secret.key

   # Создание зашифрованной копии базы данных:
   python3 scripts/backup_db.py \
       --source /app/data/keto_balance.db \
       --dest /tmp/keto_balance_final.db.enc \
       --encrypt \
       --key-file /tmp/backup_secret.key
   ```
   *Каждый зашифрованный бэкап использует криптографически стойкую соль (16 байт) и PBKDF2-HMAC-SHA256 (100 000 итераций) либо прямой Fernet-ключ.*

2. **Выгрузка копии и ключа на локальный компьютер:**
   ```bash
   # Выполняется на локальном компьютере оператора:
   scp root@<IP_СЕРВЕРА>:/tmp/keto_balance_final.db.enc ./
   scp root@<IP_СЕРВЕРА>:/tmp/backup_secret.key ./
   scp root@<IP_СЕРВЕРА>:/tmp/keto_balance_final.json ./
   ```

3. **Локальная проверка целостности (Drill Restore):**
   ```bash
   python3 scripts/restore_db.py ./keto_balance_final.db.enc \
       --target ./test_drill.db \
       --key-file ./backup_secret.key
   ```
   Убедитесь, что вывод содержит:
   `[SUCCESS] Database restored and integrity verified on ./test_drill.db`.

4. **Безопасная проверка готовности к демонтажу через скрипт:**
   ```bash
   python3 scripts/cloudru_teardown.py \
       --backup-file ./keto_balance_final.db.enc \
       --key-file ./backup_secret.key
   ```
   Скрипт выполнит dry-run, подтвердит пригодность копии и выведет список контрольных точек.

## Этап 1: Пошаговый демонтаж в консоли Cloud.ru Evolution

Откройте личный кабинет Cloud.ru: [console.cloud.ru](https://console.cloud.ru) и перейдите в проект **Keto-Balance**.

Выполняйте удаление в **строгом порядке**:

### 1.1. Виртуальные машины (Evolution Compute -> Виртуальные машины)
1. Найдите инстанс (например, `keto-balance-prod`).
2. Нажмите на меню действий `...` справа от строки инстанса -> выберите **«Удалить»**.
3. **КРИТИЧЕСКИ ВАЖНО:** В открывшемся окне подтверждения **обязательно установите галочку**:
   `[✓] Удалить подключённый системный диск (Boot Volume)`.
   *Если эту галочку не поставить, сервер удалится, но диск останется в хранилище и продолжит начислять ~10–12 ₽/ГБ каждый месяц!*
4. Подтвердите удаление.
5. **Результат проверки:** в списке «Виртуальные машины» отображается **«Нет данных» (0 машин)**.

### 1.2. Блочные диски (Evolution Compute -> Диски / Block Storage)
1. Перейдите во вкладку **«Диски»**.
2. Убедитесь, что список пуст.
3. Если отображается хотя бы один диск (со статусом `available`, `detached`, `error` или `in-use`):
   - Выберите диск -> нажмите **«Удалить»**.
   - Подтвердите удаление.
4. **Результат проверки:** в списке дисков отображается **0 дисков**.

### 1.3. Снимки дисков (Evolution Compute -> Снимки / Snapshots)
1. Перейдите во вкладку **«Снимки»**.
2. Если создавались предварительные снимки:
   - Выберите снимок -> нажмите **«Удалить»**.
3. **Результат проверки:** в списке снимков **0 записей**.

### 1.4. Публичные IP-адреса (Виртуальные сети VPC -> Публичные IP / Floating IPs)
1. Перейдите в раздел **«Сети» -> «Публичные IP»**.
2. Найдите назначенный IP-адрес.
3. **ВНИМАНИЕ:** Действие «Отвязать» (Disassociate) **НЕ останавливает списания**! Отвязанный IP продолжает тарифицироваться (~200 ₽/мес).
4. Выберите действие **«Освободить IP-адрес» (Release IP)**, чтобы вернуть адрес в пул провайдера.
5. **Результат проверки:** список публичных IP пуст **(0 IP)**.

### 1.5. Сетевые маршрутизаторы и NAT-шлюзы (VPC -> Маршрутизаторы)
1. Проверьте наличие созданных маршрутизаторов / шлюзов доступа.
2. При наличии удалите интерфейсы и сам маршрутизатор.
3. Базовую частную подсеть проекта удалять не обязательно (она бесплатна).

### 1.6. Объектное хранилище S3 (Object Storage)
1. Перейдите в раздел **«Объектное хранилище»**.
2. Если создавались бакеты для бэкапов:
   - Зайдите в бакет -> выберите все объекты -> **«Удалить»**.
   - Удалите пустой бакет.
3. **Результат проверки:** **0 бакетов**.

### 1.7. Резервные копии Cloud Backup (если настраивались)
1. Перейдите в раздел **«Cloud Backup»**.
2. Удалите цепочки резервных копий и расписания политик бэкапа.

## Этап 2: Финансовая верификация нулевого потребления (0 ₽)

1. Откройте раздел **«Биллинг» (Управление расходами) -> «Детализация расходов»**.
2. Установите гранулярность «По дням» / «По часам».
3. Убедитесь, что:
   - Текущая скорость потребления: **0.00 ₽ / час**.
   - Все строки ресурсов (Compute, Storage, Network) имеют статус отсутствия активных единиц.
4. Сделайте снимок экрана (скриншот) страницы биллинга с нулевым потреблением для архива проекта.

---

## Этап 3: Отключение проекта и защита карты

1. Если аккаунт Cloud.ru создавался исключительно под данный грант/пилот:
   - В разделе **«Проекты»** переведите проект в статус архивации или обратитесь в поддержку для закрытия проекта.
2. Проверьте раздел **«Способы оплаты»**:
   - При наличии привязанной карты убедитесь, что автоплатёж отключён или лимит расходов равен 0 ₽.
3. Зафиксируйте в журнале передачи проекта:
   - Дата и время демонтажа (UTC).
   - Подтверждение нулевых ресурсов (0 VM, 0 Disks, 0 IP, 0 Snapshots, 0 Buckets).
   - Хэш SHA-256 сохранённого локально зашифрованного архива БД.
