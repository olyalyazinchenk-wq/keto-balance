# «Кето Баланс»: конечный план от локальных наработок к Telegram и проверяемой выручке

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task, только после разрешения владельца на соответствующий пакет. Этот файл — план, не разрешение на запуск, публикацию, обработку данных или оплату.

**Goal:** Дать владельцу доступный из Telegram полезный сценарий «выбрать блюда → получить покупки → приготовить», проверить его на ограниченном добровольном пилоте и только после этого открыть один согласованный платный продукт.

**Architecture:** Сохраняем основной React 18/Vite 5/Tailwind 3 и Python/FastAPI/SQLite/python-telegram-bot; переносим из food-first только представление, через адаптеры к каноническому каталогу и домену. Сначала доказываем доступность и полезность одного пути, затем — безопасность пользовательских данных, эксплуатацию и оплату; НутриОК остаётся отдельным продуктом и не подменяет выпуск «Кето Баланс». Новые ИИ-сервисы, микросервисы и оркестраторы не нужны для первого результата.

**Tech Stack:** существующие Node/TypeScript/React, Python, тесты node:test/unittest; инструменты браузера для проверки; согласованный HTTPS-хостинг для внешнего входа, не предполагаемый сервер на ПК.

**Статус:** предложенная этапность и исполнительный контракт. Продуктовый код в этом ходе не изменяется. Цены, платёжные условия, содержание, инфраструктура и обработка реальных данных не утверждаются этим планом.

## 1. Что именно должен получить владелец

Не очередной отчёт «23 теста прошли», а последовательно три разных результата:

1. **Показ:** владелец открывает конкретный вход в Telegram и видит текущий результат, а не localhost/старую сборку.
2. **Польза:** взрослый доброволец без подсказок разработчика выбирает доступные блюда, получает связанный список продуктов и может приготовить хотя бы одно из них. Медицинская пригодность рациона этим не устанавливается.
3. **Покупка:** после утверждения предложения человек понимает состав, срок, сумму и ограничения; подтверждённая оплата даёт ровно обещанный доступ; возврат и поддержка действительно работают.

Первый показ, закрытый бесплатный пилот, платный пилот и публичный выпуск — разные статусы. Ни один предыдущий статус не разрешает следующий автоматически.

## 6. Архитектурный контракт и границы доверия

### 6.1 Целевой путь

```text
Telegram-вход
  → основное приложение, текущий release ID
  → короткие настройки и понятная граница безопасности
  → канонический menu controller / проверенный каталог
  → Today → Menu → Recipe → Shopping
  → при необходимости настоящий канал личной поддержки

После отдельной готовности:
  Telegram initData → серверная валидация → сессия
  → только свои записи / серверные роли / серверные права доступа
  → Stars order → trusted successful_payment → entitlement
```

Рецепт в каноническом домене: `src/domain/types.ts`, строковый `id`, `ing: [string,string][]`, `steps: string[]`, `time`, `serv`. Меню: `src/domain/menu.ts`, `days[].date`, `slots: Record<string,string>`, `created: number`. Не подменять дату `dayIndex`, строковый ID — индексом массива, ссылку — вложенным объектом.

Один источник рецептов для основного пути — `src/data/recipes.ts`; ручное второе объявление `RECIPES` в старом `src/App.tsx` не может оставаться источником нового пути. Само переключение на каталог не доказывает его достоверность: допуск содержания — отдельный gate.

- Представление не рассчитывает питание, цены и медицинские показатели.
- Только проверенное `src/core/keto-engine/` по отдельно утверждённой методологии может выдавать нутриентные расчёты. Существование файла ядра не является приёмкой.
- Неизвестные нутриенты и цены показываются `[УТОЧНИТЬ]` или не показываются; не вычислять «правдоподобно» и не подставлять ноль.
- В генерации, замене и после изменения ограничений один и тот же допуск рецептов. Нет подходящих вариантов — честное пустое состояние, без снятия ограничений.

### 6.2 Хостинг: что решено и что нет

Для **показа без личных данных** предлагается один согласованный static preview на Cloudflare Pages Direct Upload. Это выбранный кандидат, не приобретение услуги и не утверждение доступности аккаунта. Документация описывает загрузку уже собранных assets через web-интерфейс или Wrangler [S3]; доступность аккаунта, лимиты и доступность из сети владельца ещё не проверены. Это не рекомендация покупать тариф или переносить backend туда автоматически.

Для backend с приватными данными и платными обязательствами нужна отдельно выбранная и разрешённая постоянная среда с persistent storage, TLS, backup/restore и ответственным. До реальных пользовательских данных проверить шифрование at rest и отдельное хранение ключа для БД, резервных копий и иных сохраняемых пользовательских данных [S5]. Не изобретать собственную криптографию и не включать шифрование диска/перенос данных без отдельного согласования; отсутствие проверенного механизма блокирует сбор таких данных. Сервер не считается существующим. VPN-сервер из настроек ПК не разрешён для приложения.

При использовании различных origin для frontend/API до реальных данных отдельно проверяются cookies, CORS, CSRF и вход из Telegram WebView. Для первого серверного пилота предпочтителен единый origin; не создавать вторую auth-схему ради static host.

Нет approved backend host — подготовку можно продолжить на синтетических данных, но K2 с серверными записями и K3 не приняты. Работающий ПК/туннель не выдаётся за круглосуточную услугу.

### 9.4 Premium-ограничители вкуса

Сохранять: тёплый светлый фон, натуральные акценты, читаемый sans, крупное соответствующее блюду фото, простой заголовок, одну ясную основную кнопку. Общение на «ты», без назидания и чрезмерного emoji.

Запрещены: газетные колонки, «выпуски», музейные подписи и тарелка-экспонат, decorative technical rails, псевдонаучные шкалы энергии/талии/дофамина, выдуманные отзывы/регалии/таймеры дефицита. Не улучшать доверие ложной точностью.

Проверки на **320×640 и 390×844**:

- заголовок и CTA читаются без zoom, ключевая кнопка не скрыта навигацией;
- `document.documentElement.scrollWidth <= document.documentElement.clientWidth`;
- последний блок и controls доступны над нижней панелью/safe area;
- одна текущая навигация во всех четырёх экранах;
- light/dark Telegram не ломает контраст, фото/placeholder не меняют смысл блюда;
- фокус, label кнопок и состояние pending/error видимы;
- увеличенный текст не превращает экран в горизонтальный скролл.

Одна ограниченная коррекция после сквозного прохода. Косметические пожелания без блокировки сценария — backlog после показа, а не повод не выпускать.

## 11. Пакет D — полезный бесплатный пилот и сохранение PB-объёма

### 11.1 Предложенный минимальный договор пилота

На согласование: **до трёх взрослых добровольцев**, не массовый запуск. Это выбранный размер управляемого исследования, не статистическая оценка рынка. До приглашений владелец утверждает точное число/текст/данные/удаление.

Первый полезный объём — один законченный день с одобренными блюдами, понятными исходными выходами и связанными покупками; затем расширение до согласованного состава разового старта. Пока данные синтетические или количества не приняты, это usability-test, а не работающий сервис меню.

События исследования: `opened_current_build`, `menu_viewed`, `recipe_opened`, `shopping_rebuilt`, `flow_completed`, `returned_next_planning`, позднее `checkout_started`, `payment_confirmed`, `refund_confirmed`.

Не внедрять внешний tracker ради этих событий. Для первых согласованных наблюдений достаточно `docs/release/pilot-observations.csv`; только обезличенные case_id и факты действий. Даже обезличивание/псевдонимизация не заменяет согласованных правил обработки. Тексты здоровья, дневника, raw Telegram ID/initData, контакты и медицинские сведения в аналитику не копируются.

Знаменатели фиксируются явно: приглашённые ≠ открывшие ≠ завершившие ≠ оплатившие. Продление считается только для действительно наступившего периода, а не по всем пользователям на третий день.

### 12.2 Предложенные заранее правила решения

Это **рабочие пороги для маленького пилота, на утверждение владельца**, не отраслевые нормы:

- **Продолжать к предложению покупки:** завершённый безопасный путь подтверждён; минимум двое из трёх добровольцев смогли самостоятельно получить меню/покупки; есть фактический пример бытовой пользы и понятная причина пользоваться дальше. При другом согласованном числе участников сначала пересмотреть порог, не манипулировать знаменателем.
- **Исправить, а не расширять:** участники хотят результат, но систематически останавливаются на одном шаге. Исправить только этот шаг и повторить сценарий.
- **Не строить подписку:** пользователям нужен только разовый набор, а к следующей неделе они не возвращаются. Проверить законченный разовый продукт; не придумывать искусственную зависимость.
- **Не масштабировать продажи:** реальная выручка/положительная маржа не подтверждены, владелец перегружен, возвраты/поддержка не управляются.
- **Немедленный STOP:** утечка/чужие данные, ложная персонализация/медицинские обещания, неавторизованная выдача, доступ до подтверждения оплаты, непонятные расходы или нарушение согласия.

Ноль покупок на трёх добровольцах не доказывает отсутствие рынка; это сигнал проверить оффер и пользу, а не построить больше функций. Один платёж тоже не доказывает product-market fit.

### 12.3 Что оставляет пользователя добровольно

Следующая неделя собирается проще благодаря сохранённым подходящим блюдам, понятным покупкам и возможности менять план. Причина платить — удобство повторяющейся бытовой задачи. Не блокировать собственные записи, безопасность, отмену и поддержку ради удержания.

## 13. Пакет E — один платный продукт, затем подписка

### 13.1 Рекомендуемое коммерческое направление

Сохраняем подтверждённую владельцем лестницу: **бесплатное знакомство → небольшой самостоятельный разовый старт → месячная подписка**. Для первого платного теста предлагается один законченный старт; кандидат «Спокойный старт: неделя без хаоса в меню» из существующей стратегии, но срок/состав/цена ещё не утверждены.

Не делать НутриОК коммерческим приоритетом автоматически только потому, что его бот уже запущен. Если владелец отдельно выбирает НутриОК для первой выручки, работа идёт в N с его продуктовым контрактом и отдельной платёжной/клинической проверкой; Keto-тарифы и обещания туда не переносятся.

Цифровые товары и услуги внутри Telegram проектировать через **Stars/XTR**; существующие RUB/manual сценарии не считать готовым разрешённым решением для нового цифрового продукта [S2]. Классификацию человеческого сопровождения, статус продавца и юридические обязательства не выводить из названия услуги.

Клиентский ориентир 500–1 000 ₽ из интервью — не утверждённая Stars-цена и не поступление владельцу. 49/99/199/299 Stars из исследования не становятся тарифами этим планом.

## 14. Специальные риски НутриОК — не переносить их в текущий Keto-срез

Если после TG0 владелец поручает полноценную B7/платную приёмку НутриОК, это отдельный пакет с его writer и согласованием:

- Не импортировать `tests/test_review_gate.py` вслепую: он импортирует `main`, который может читать настройки/создавать I/O. Сначала проверить импортную цепочку и изолировать synthetic settings/storage/network.
- Создать чистый `tests/test_review_gate_artifact_binding.py`: без `main`/`storage`, только `review_gate` и `nutriok_product`; fixtures в разрешённом scratch. Проверить approved record без hash, legacy approved без hash, missing PDF, tampered PDF, mismatched path, valid binding.
- RED по исходнику ожидается на missing-hash случаях. Не выполнять пробы на реальных отчётах.
- Возможное минимальное исправление — требовать непустые корректные hash и path и совпадение содержимого; ошибки I/O fail-closed. Оно может скрыть старые материалы: **без ручного решения владельца нельзя применять миграцию/перевыдачу/переписывание approvals**.
- Safety gate: проверить все ранее названные пропуски/отрицания синтетически, но не объявлять полный медицинский фильтр доказанным на одном наборе фраз. Утверждённый clinical scope и квалификация проверяющего — отдельные prerequisites.
- Полная B7: реальная выдача допустимого результата, запрет выдачи недопущенного, owner review, reply, user-owned data isolation. TG0 бесплатного первого шага этого не заменяет.
- Существующие RUB/manual paid paths нуждаются в проверке классификации/правил платформы; показ суммы в коде не является новым разрешением продавать.

Не использовать этот список как повод бесконечно откладывать безопасный бесплатный показ или silently менять чужой рабочий бот.

## 15. Приёмка, которой нельзя подменить результат

### 15.1 Матрица доказательств

| Уровень | Обязательное доказательство | Недостаточно |
|---|---|---|
| Source | Актуальные safe paths, diff/hash, entrypoint trace | Скрин чужого репозитория, имя модели |
| Local tests | Команда, collection/pass/fail/error/skip, exit, время, runtime | «Всё зелёное», ноль collected |
| Local UI | Один связный browser-протокол на текущем bundle | Только SSR/source literal tests, один красивый PNG |
| External | Точный HTTPS URL, HTML/JS/CSS identity, внешний GET | Tunnel process running, successful deploy API |
| Telegram | Владелец открыл точной кнопкой и прошёл сценарий на том же build | Обычная вкладка браузера, localhost |
| Utility | Фактическое выполнение бытовой задачи добровольцем | Число экранов/рецептов/агентов |
| Safety/privacy | Негативные owner/role/data/permission тесты, утверждённая область содержания | Client flag, дисклеймер, одобрение владельцем вместо клинической экспертизы |
| Paid | Approved offer + реальный подтверждённый charge/access/refund в согласованном тесте | Кнопка, invoice создан, fake paid, ручной флаг premium |
| Business | Реальные поступления/расходы/нагрузка/повторное использование | Цель 80 000 ₽, размер подписчиков, выдуманная конверсия |

### 15.2 Формат единственного статуса

После разрешения исполнения создать/вести `docs/release/acceptance.md`, а существующий `docs/release/status.md` согласованно обновлять ссылкой на него, не затирать чужие evidence.

```text
Gate: K0 / K1 / K2 / K3 / K4 / TG0
Status: NOT_RUN | IN_PROGRESS | PASS | FAIL | BLOCKED_<reason>
Observed at: дата/время/часовой пояс
Scope: prototype / integrated-local / external-demo / real-client / paid-pilot
Source: ветка + HEAD + хеши затронутых uncommitted safe files
Artifact: build ID + exact HTML/JS/CSS SHA-256
Entry: точный test bot/menu entry и HTTPS URL, без токенов
User action: что человек сделал и что получил
Checks: команда → collected/pass/fail/error/skip → exit → evidence path
Owner confirmation: кто, когда, что именно подтвердил
Limitations: что не проверено и что НЕ входит
Next blocker: один следующий шаг, ответственный, контрольная точка
```

Запись PASS — организационная приёмка, а не автоматически действующая техническая блокировка. Если board/CI hook не подключён и негативно не проверен, не утверждать, что система «не позволит» отметить Done. Независимый проверяющий обязан вернуть FAIL/BLOCKED при отсутствии обязательных доказательств.

### 15.3 Процедура моего независимого review

1. Получить отчёт по шаблону и точный scope; не просить весь чат.
2. Прочитать затронутые реализации и тесты, проверить актуальность исходников и безопасность запусков.
3. Пройти фактический entrypoint, данные, callbacks, persistence и внешние операции.
4. Повторить разрешённые mandatory suites и browser-случаи. Проверить не только happy path, но соседние/ошибочные состояния.
5. Сравнить served JS **и** CSS с принятой сборкой; не делать вывод по `/src/...`, который может отдавать SPA HTML.
6. Для внешних действий прочитать точный изменённый target назад. Для Telegram и платежей получить owner evidence в заранее согласованных пределах.
7. Выдать краткий вердикт `принято / принято только локально / не принято`, таблицу фактических проверок и максимум три блокирующие коррекции.
8. Не открывать новую архитектурную дискуссию, если критерии выполнены. После PASS двигаться к следующему gate, не добавлять polish бесконечно.

## 16. Эксплуатация и завершение разработки текущего среза

До платного пилота обязательны:

- Названный runtime owner и реально подтверждённое время доступности. Если это ПК — честное ограниченное окно, либо отдельно принятый постоянный host; не обещание 24/7.
- Проверенный backup и **restore в отдельную синтетическую среду**, не просто скопированный файл. Не читать/переносить боевую БД.
- Сохранённый предыдущий артефакт/кнопка и согласованный scoped rollback; не `git reset --hard`, не `clean/stash` чужой работы.
- Health/version без секретов; журналы без initData/токенов/здоровья; разрешённый контроль работоспособности, не бесконечные фоновые задачи.
- Зафиксированный stop-selling/unavailable сценарий при сбое и назначенная поддержка.
- Одно owner-approved приглашение в пилот; перед публикацией прочитать обратно точный текст/target, никакой массовой рассылки по умолчанию.

**Разработка текущего среза завершена**, когда критерии своего gate выполнены и независимо приняты. Все дополнительные пожелания — новый согласованный пакет. «План выполнен» не равно «продукт принят».

## 17. Инструменты и навыки: минимальный достаточный набор

Нужные существующие навыки при исполнении: `subagent-driven-development`, `test-driven-development`, `requesting-code-review`, `telegram-bot-development`, `systematic-debugging`; для действия в существующем окне — соответствующий browser/computer-use skill. Для Hermes-настроек сначала `hermes-agent`, но здесь изменение Hermes не является prereq.

Устанавливать новые plugins/MCP, подключать Refero/Mobbin/генерацию изображений/внешнюю память/AI pipeline **не требуется**. Эти инструменты не исправляют неправильно направленный внешний вход или неподключённый домен. Если реально отсутствует одна нужная возможность, исполнитель пишет: какую конкретную проверку она блокирует, минимальную альтернативу, источник документации, стоимость/данные и отдельное согласование. Исследование не равно установке.

Допускается один implementer и один независимый read-only reviewer; больше агентов — только для независимых непересекающихся задач. Не расходовать бюджет/контекст на повторные обзоры уже принятого компонента без новой причины.

```ts
export function resolveSelectedDay(
  saved: unknown,
  days: ReadonlyArray<{ dayIndex: number }>
): number | null {
  if (days.length === 0) return null;
  if (
    typeof saved === 'number' &&
    Number.isInteger(saved) &&
    days.some((day) => day.dayIndex === saved)
  ) {
    return saved;
  }
  return days[0].dayIndex;
}
```

### B.2 Реализация

Create `src/adapters/foodView.ts`:

```ts
import type { GeneratedMenu, Recipe } from '../domain/types';
import { getSlotKeys } from '../domain/menu';

export interface FoodRecipe {
  id: string;
  title: string;
  minutes: number;
  sourceYield: number;
  ingredients: { name: string; amount: string }[];
  steps: string[];
  nutritionStatus: '[УТОЧНИТЬ]';
}

export interface FoodDay {
  date: string;
  slots: { key: string; recipe: FoodRecipe }[];
}

export function toFoodRecipe(recipe: Recipe): FoodRecipe {
  return {
    id: recipe.id,
    title: recipe.title,
    minutes: recipe.time,
    sourceYield: recipe.serv,
    ingredients: recipe.ing.map(([name, amount]) => ({ name, amount })),
    steps: [...recipe.steps],
    nutritionStatus: '[УТОЧНИТЬ]',
  };
}

export function projectFoodDay(
  menu: GeneratedMenu,
  selectedDate: string,
  recipes: readonly Recipe[]
): FoodDay {
  const day = menu.days.find((item) => item.date === selectedDate);
  if (!day) throw new Error('Выбранный день отсутствует в текущем меню.');
  const byId = new Map(recipes.map((recipe) => [recipe.id, recipe]));
  const slots = getSlotKeys(menu.meals).map((key) => {
    const id = day.slots[key];
    const recipe = byId.get(id);
    if (!recipe) throw new Error(`Не найден рецепт для слота ${key}.`);
    return { key, recipe: toFoodRecipe(recipe) };
  });
  return { date: day.date, slots };
}
```

Карта: `time → minutes`, `serv → sourceYield`, `ing[][0/1] → name/amount`, `steps → copy`, `days[].date → date`, `slots key → requested meal slot`. Не выводить raw `serv` как «порция пользователя» и не делить количества без утверждения semantics.

Повреждённые внешние payloads валидируются на границе хранения/API; этот типизированный адаптер не заменяет такой валидатор и не объявляется security gate. Missing references не маскируются fallback-рецептом.

```ts
import type { Recipe } from './types';

export function selectReleasedRecipes(
  recipes: readonly Recipe[],
  releasedIds: readonly string[]
): Recipe[] {
  if (
    !Array.isArray(releasedIds) || releasedIds.length === 0 ||
    releasedIds.some((id) => typeof id !== 'string' || id.length === 0) ||
    new Set(releasedIds).size !== releasedIds.length
  ) {
    throw new Error('Набор допущенных рецептов не утверждён или повреждён.');
  }
  const byId = new Map(recipes.map((recipe) => [recipe.id, recipe]));
  if (byId.size !== recipes.length) {
    throw new Error('В исходном каталоге повторяются идентификаторы.');
  }
  return releasedIds.map((id) => {
    const recipe = byId.get(id);
    if (!recipe) throw new Error(`Допущенный рецепт ${id} отсутствует в каталоге.`);
    return recipe;
  });
}
```

```ts
import {
  generateMenu, replacementCandidates, type GenerateMenuOptions,
} from '../domain/menu';
import type { Recipe, UserProfile } from '../domain/types';
import { selectReleasedRecipes } from '../domain/releaseCatalog';
import { RECIPES } from '../data/recipes';
import { RELEASED_RECIPE_IDS } from '../data/releasedRecipeIds';

interface ReplacementRequest {
  currentId: string;
  dayIds: string[];
  profile?: UserProfile | null;
  preferredCat?: string;
  mode: 'keto' | 'carnivore';
}

export function createMenuController(
  catalog: readonly Recipe[],
  releasedIds: readonly string[]
) {
  const getReleasedRecipes = () => selectReleasedRecipes(catalog, releasedIds);
  return {
    getReleasedRecipes,
    createUserMenu(options: GenerateMenuOptions) {
      return generateMenu(getReleasedRecipes(), options);
    },
    createUserReplacementCandidates(request: ReplacementRequest) {
      const recipes = getReleasedRecipes();
      if (request.mode !== 'keto' && request.mode !== 'carnivore') {
        throw new Error('Недопустимый режим замены.');
      }
      if (!recipes.some((recipe) => recipe.id === request.currentId)) {
        throw new Error('Текущее блюдо больше не допущено; пересобери меню.');
      }
      return replacementCandidates(
        request.currentId, request.dayIds, recipes,
        request.profile, request.preferredCat, request.mode
      );
    },
  };
}

const liveController = createMenuController(RECIPES, RELEASED_RECIPE_IDS);
export const createUserMenu = liveController.createUserMenu;
export const createUserReplacementCandidates =
  liveController.createUserReplacementCandidates;
export const getReleasedRecipes = liveController.getReleasedRecipes;
```

## Приложение F. Точные manifests технических gates без навязывания отложенных функций

Это изменения **существующего** `scripts/verification.py`, не новый оркестратор и не уже подключённая блокировка. Вводить после безопасного I01–I05, по TDD. ### F.1 Scope и момент исполнения

- `k1-local`: основной интегрированный read-only пример, исходные строки shopping, отсутствие fake claims/неразрешённого I/O. Без auth/diary/admin/reminders/платежей. Browser и Telegram-показ C09–C14 обязательны отдельно, не объявляются E2E suite, если выполнены вручную.
- `k2-pilot`: K1 + утверждённые количества/покупки, auth/session/свои документы, support, допуск каталога, data rights и эксплуатационный минимум. Без дневника/админки/напоминаний только если этапность явно утверждена; эти функции выключены и не входят в обещание.
- `k3-pilot`: K2 + один разовый оффер/order/payment/access/refund, без автопродления. При утверждении другого scope manifest пересматривается **до** исполнения, не после провала тестов.
- Полный исходный `free/paid` остаётся обязательным для соответствующего полного PB-выпуска. Нельзя заменить его новым сокращённым stage и назвать весь PB-объём готовым.

Для каждого listed suite файл должен существовать и собрать ненулевое число тестов. Ни file-exists stub, ни один зелёный suite вместо отсутствующих остальных не проходят. Новые перечисленные test-файлы создаются в пакетах реализации/по техническому контракту; их отсутствие сейчас ожидаемо и блокирует будущий stage, а не разрешает создать пустышку.

```python
K1_FRONT = tuple(dict.fromkeys(P0_FRONT + (

    'test_products', 'test_billing_orders', 'test_stars_handlers',
    'test_entitlements', 'test_refunds', 'test_release_gate',

def build_product_plan(root: Path, stage: str) -> list[Step]:
    back = {
        'k1-local': K1_BACK, 'k2-pilot': K2_BACK, 'k3-pilot': K3_BACK,

             '--suite', f'tests.backend.{name}'),
            ('scripts/run_backend_tests.py', f'tests/backend/{name}.py'),

            ('node', '--test', '--test-reporter=tap', file), (file,), 'tap',

    steps.extend((

        Step('Build', (npm, 'run', 'build'), ('scripts/stamp-release.mjs',)),

    if stage != 'k1-local':
```
